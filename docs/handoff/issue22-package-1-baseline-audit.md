# Issue #22 package 1 baseline audit

Status: complete on 2026-06-04. This audit is non-mutating and does not use private or owner books.

## Exact current blocker

GitHub #22 remains open because the repository still lacks an actual isolated GnuCash Desktop-generated synthetic SQLite fixture that passes both:

1. fail-closed Desktop fixture candidate preflight; and
2. default-read-only validation with `GNUCASH_WRITES_ENABLED=false`.

The latest #22 issue body asks for disposable fixtures generated by real GnuCash Desktop versions. The latest comments before this package still classify #22 as open and state the remaining safe next step as: isolated disposable GUI/manual-safe Desktop environment -> create/save synthetic SQLite fixture -> fail-closed candidate preflight -> default-read-only validation.

## Existing evidence categories

Current compatibility docs separate evidence as follows:

- generated synthetic fixtures: accepted as narrow tested synthetic/disposable SQLite evidence, including the committed test fixtures and the generated `compatibility-v1` fixture path;
- Desktop-generated synthetic SQLite fixture: missing; metadata/candidate helpers exist, but no actual Desktop-generated fixture has been created or validated;
- owner copied/restorable W3 evidence: accepted only as narrow #36 copied-book dogfood/readiness evidence and not as a #22 Desktop-version fixture row;
- unsupported private/real books: not valid public fixture evidence and must not be committed or used for #22.

## Existing safe workflow

The repository already supports safe metadata/validation workflow for future Desktop candidates:

- `apps/api/scripts/collect_gnucash_compatibility_metadata.py` reads a copied/disposable SQLite book in read-only SQLite mode and emits redacted metadata only.
- `scripts/preflight_desktop_fixture_candidate.py` validates JSON metadata and fails closed for missing Desktop/synthetic markers, unsupported backend, private-looking fields, copied/private scope, and missing default-read-only validation marker.
- `apps/api/app/compatibility_matrix.py` keeps Desktop-generated metadata blocked/manual until explicit read-only validation and preflight markers pass.
- `scripts/check_public_status.py` guards current public compatibility wording.

Safe raw fixture storage policy remains conservative: generated GnuCash books, SQLite DBs, app DBs, backups, CSV exports, screenshots, private paths, account names, transaction descriptions, memos, and amounts must not be committed. A raw synthetic Desktop-generated fixture may only be handled outside git unless a later explicit fixture policy allows a committed binary.

## Environment capability preview

The current host has `gnucash-cli` and `gnucash` installed, but the non-GUI probe and command help show no safe noninteractive create/save SQLite fixture command. There is no `DISPLAY`, no `xvfb-run`, no `Xvfb`, and no `xdotool` on `PATH`; `gnucash --version` cannot initialize the GUI without a display. Therefore this environment is not currently capable of safely generating a Desktop GUI fixture without adding GUI/Xvfb tooling or using a separate isolated manual Desktop environment.
