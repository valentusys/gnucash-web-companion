# v0.1.2-readonly Release Notes

> Draft release-prep artifact only. Prepared in Phase 115 for a possible future GitHub pre-release.
>
> Publication is not authorized in Phase 115. No `v0.1.2-readonly` tag, GitHub release, package, or public release state change was created by this phase.

## Status

`v0.1.2-readonly` is a conservative pre-alpha read-only maintenance candidate after the published `v0.1.1-readonly` pre-release.

The project remains read-only by default. GnuCash Desktop remains the authoritative editor. This project is not production-ready, not security-audited, and not a hosted financial service. Test with disposable fixtures or copied GnuCash SQL books first, keep backups, and do not expose early deployments directly to the public internet.

Controlled-write code may exist in the repository as experimental post-MVP work, but it is outside this read-only maintenance candidate and remains disabled by default:

```text
GNUCASH_WRITES_ENABLED=false
```

## What changed since v0.1.1-readonly

This candidate summarizes the read-only user-facing and operator-facing work completed in Phases 106–114:

- Phase 106: added a read-only transaction state/reconciliation filter using confirmed GnuCash split `reconcile_state` values. Transaction list, count, account-scoped lists, and CSV export share the same `transaction_state` contract for `unreconciled`, `cleared`, `reconciled`, and `voided`.
- Phase 107: added URL-only transaction filter reset/preset UX. `Clear filters` removes active query/account/date/amount/state filters without browser storage, and CSV export preserves the active filter query string.
- Phase 108: brought account-detail transaction lists closer to transaction-list parity: account-scoped search, date presets/custom dates, amount range, split reconciliation state filters, pagination, filtered counts, empty-state explanation, and CSV export parity.
- Phase 109: added conservative read-only scheduled/recurring transaction awareness through authenticated API/UI surfaces. The app exposes only safe summary metadata and does not expose template splits, raw SQL dumps, private paths, amounts, fake next-run predictions, or editing controls.
- Phase 110: hardened `/books` as a read-only metadata/status page with explicit access role/status/read-only metadata, safe book-context links, and no upload/delete/registry/default-management controls.
- Phase 111: refreshed compatibility fixture evidence with a safe Desktop/CLI tooling probe. The local environment had no `gnucash`/`gnucash-cli`, so no Desktop-generated fixture or broad Desktop-version claim is made.
- Phase 112: added LAN/VPN deployment safety diagnostics for wildcard CORS outside development-like environments, including non-secret startup/health warnings and exact origin examples in docs.
- Phase 113: added a Russian accounting/safety glossary and localized a narrow transaction filter/export UI slice while keeping English canonical, Russian partial, and safety warnings intact.
- Phase 114: ran a synthetic/disposable Docker/Caddy browser/API dogfood refresh across login, dashboard, accounts, books, scheduled awareness, account detail, transaction filters, transaction detail, CSV export, and disabled-write probes with `GNUCASH_WRITES_ENABLED=false`.

## Read-only maintenance value

The candidate is meaningful because it improves everyday read-only browsing and operator confidence without expanding write scope:

- better transaction filtering and CSV parity;
- better account-detail filtering/export consistency;
- safer scheduled-transaction visibility without editing;
- clearer multi-book metadata/status UX;
- practical CORS exposure diagnostics for LAN/VPN deployments;
- narrow Russian terminology consistency for safety-sensitive UI copy;
- synthetic browser dogfood evidence after the UX/filter changes.

## Known limitations and non-claims

This candidate does not claim:

- production readiness;
- security audit completion;
- safe direct public-internet exposure;
- broad compatibility with every GnuCash Desktop version or every backend;
- PostgreSQL, MySQL, MariaDB, XML-book, or arbitrary real-world-book compatibility;
- successful personal copied-book dogfood after these changes;
- hosted SaaS readiness;
- collaborative accounting, family-wallet positioning, or real-time multi-user editing;
- account, transaction, invoice, bill, customer, vendor, scheduled-transaction editing, CSV/OFX import, or banking integrations;
- safe production write mode for real books.

GitHub #38 remains open and blocked until a safe copied personal GnuCash SQL book is available outside git for a local-only dogfood rerun. Phase 114 dogfood used only synthetic/disposable data and must not be described as personal-book dogfood.

Compatibility evidence remains intentionally narrow: committed synthetic/disposable SQLite fixtures, copied/disposable metadata procedures, and safe local tooling probes. Users must test their own copied book before relying on the app for regular read-only browsing.

## Upgrade notes from v0.1.1-readonly

1. Back up app metadata and any copied test books used with the app.
2. Review `.env.example` and keep `GNUCASH_WRITES_ENABLED=false`.
3. After a future authorized publication, check out the published `v0.1.2-readonly` tag.
4. Rebuild/restart Docker Compose.
5. Run `/api/health`, login, dashboard, accounts, books, scheduled awareness, transactions, account detail, transaction detail, CSV export, and disabled-write checks on disposable or copied data before regular use.
6. Keep `.env`, app DBs, GnuCash books, backups, real financial exports/screenshots, secrets, tokens, keys, and certs out of git.
