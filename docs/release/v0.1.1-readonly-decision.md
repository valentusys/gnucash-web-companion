## Why not prepare v0.1.1-readonly now

There is a useful post-release maintenance change set, especially Phases 81–84 and 90–93. However, a maintenance release candidate should not be prepared while an active read-only export correctness issue remains open and reproducible:

- GitHub #39: CSV export row count is capped at 500 despite 10,000-row export headers.

The issue affects a read-only user-facing export path and was observed repeatedly in the synthetic benchmark evidence after Phase 87, Phase 88, and Phase 89. Because Phase 84 specifically advertised export truncation/limit headers, packaging a maintenance release before resolving #39 would risk shipping inconsistent CSV export behavior.

A second blocker remains non-code/runtime-evidence related:

- GitHub #38: copied personal-book dogfood rerun still needs a safe copied personal SQL book outside git.

#38 does not block a narrow synthetic-data-only maintenance fix by itself, but it means the project still must not claim successful personal-book dogfood coverage for the maintenance release.

## Required before preparing v0.1.1-readonly

Minimum next release-prep gate:

1. Fix #39 with a regression test proving CSV body row count and export headers agree for more than 500 rows, without enabling writes or changing the read-only safety boundary.
2. Rerun the required backend/frontend/Docker config checks.
3. Rerun the synthetic benchmark or an equivalent targeted export smoke proving the #39 mismatch is resolved.
4. Keep `GNUCASH_WRITES_ENABLED=false` as the default.
5. Do not claim production readiness, security audit status, broad GnuCash compatibility, or successful personal-book dogfood unless supported by separate evidence.
6. Only after the above, create `docs/release/v0.1.1-readonly-notes.md` and a checklist in a separate explicit release-preparation phase.
