# v0.4 owner-writebeta readiness remains unreleased

Status: `UNRELEASED_UNTIL_OWNER_APPROVAL`.

This document explains the release boundary for #36 without preparing a release,
tag, package, image, or public write-beta claim. The companion boundary doc is
[owner-writebeta owner-approval boundary](owner-writebeta-owner-approval-boundary.md).

## Reader summary

Owner-writebeta readiness work is maintenance evidence only. It records that some
controlled-write checks and one narrow copied-book dogfood path have been reviewed.
It does not mean owner-writebeta is available for general use, public beta use, or
real/private/original/working/only-copy book mutation.

The current public release remains `v0.5.0-public-readonly-beta`. The
`v0.4.0-owner-writebeta` line is not published and must stay unreleased unless the
owner explicitly approves a later release-candidate package.

## Why no release is published

The blocker is not just test status. It is an ownership and public-signal decision:
clean local checks can support repository hygiene, but they cannot convert bounded
maintenance evidence into release authorization.

Treat the current state as an approval boundary, not as a nearly finished release.
The repository can record that evidence was reviewed, but only the owner/PM can
decide whether that evidence is enough to prepare a release-candidate package. A
docs worker must therefore preserve the no-release state even if every local guard
passes.

Read this document as a no-release explanation, not as a release checklist. Its
purpose is to keep reviewer expectations aligned while #36 remains open and the
owner has not approved release-candidate preparation.

1. #36 is still open. The owner has not approved closure of all remaining
   controlled-write readiness gates.
2. The accepted W3 evidence is deliberately narrow: one staged outside-git
   copied/restorable target, exact operation counts, and redacted evidence only.
3. Supported-version write compatibility is not accepted as a release claim.
4. Real/private/original/working/only-copy book mutation is outside the approved
   evidence scope and remains unauthorized.
5. A release artifact would be easy to misread as public write beta availability or
   broader write safety. The repository must avoid that signal until owner approval.

## Approval-state flow

Use this flow for future status edits:

```text
evidence reviewed -> maintenance docs updated -> owner/PM approval missing -> no release
```

The flow stops at no-release unless a later prompt explicitly changes the state.
Do not infer approval from phrases such as "ready", "green checks", "accepted
evidence", or "handoff complete". In this packet those phrases can describe only
maintenance evidence.

## Owner approval boundary

Owner approval is not implied by a clean repository, a completed handoff, or a
readiness summary. It must be an explicit later decision that names the scope and
allows release-candidate preparation for that scope.

Approval also is not implied by the quantity of conservative documentation. A set
of no-release pages, handoffs, and green guard outputs is still only evidence that
the repository is documenting the boundary consistently. It cannot replace the
missing owner/PM decision to accept public-signal risk for a named owner-writebeta
scope.

Until that decision exists, these docs remain maintenance records only:

- they may explain why owner-writebeta stays unreleased;
- they may link the accepted narrow copied/restorable evidence;
- they may list blockers and conservative next steps;
- they must not become release notes, final gates, package instructions, or
  announcement copy.

If a future owner-approved task changes the state, that task must still preserve
the default-disabled write posture and `APP_ENV=test` gate unless it separately
authorizes a narrower, reviewed change. This document does not authorize that
change.

## Why this matters to readers

Release artifacts are public signals. A tag, release page, package, image, or
announcement can be read as permission to try owner-writebeta outside the narrow
accepted evidence. That would overstate the current state. Keeping the readiness
material unreleased avoids implying public availability, broad compatibility, or
real-book safety before the owner accepts that risk and scope.

## Review-order guidance

When reviewing future #36 notes, read release authorization before release
readiness. A document may say that a guard passed, a blocker was narrowed, or a
handoff was accepted. Those statements still remain subordinate to the current
release state unless the same task explicitly authorizes release-candidate
preparation.

Do not re-order the decision as "evidence first, approval later". That wording
can make owner approval look like the final item in a worker checklist. The safe
order is:

```text
owner/PM release-candidate approval missing -> evidence remains maintenance-only
```

This preserves the no-release state even if later maintenance work improves local
confidence, issue navigation, or redacted evidence summaries.
