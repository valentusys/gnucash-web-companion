# v0.4 owner-writebeta no-release decision

## PM decision

Do not prepare, tag, publish, or claim `v0.4.0-owner-writebeta` in this package.

## Why

- W3 copied-book evidence is accepted narrowly, but only for one staged outside-git copied/restorable
  target and exact CREATE 2 / PATCH 1 / DELETE 1 operation counts.
- #36 remains open for remaining controlled-write gates, PM closure acceptance, real-book boundary,
  and supported-version compatibility posture.
- #22 is closed narrowly for one Desktop-generated synthetic SQLite fixture, but that closure is
  read-only synthetic evidence only and does not prove owner-writebeta write compatibility.
- #28 was improved for release-reviewer readability, but readability cleanup is not a reason to
  publish writebeta.
- A pre-release now could still be misread as public write beta or broader real-book/write safety.
- Passing repository health checks do not override the missing owner approval for release publication.
- Owner approval is the release-state switch; until that switch exists, readiness docs stay
  maintenance-only and must not become release-candidate artifacts.

## What remains true

- Public read-only beta remains `v0.5.0-public-readonly-beta`.
- `v0.5.1-public-readonly-beta` is not published.
- `v0.4.0-owner-writebeta` is not published.
- `GNUCASH_WRITES_ENABLED=false` remains default.
- Enabled write-alpha/writebeta remains `APP_ENV=test` gated.
- No public write beta, stable, production-ready, security-audited, broad compatibility, or
  only-copy safety claim is made.

## Documentation boundary

Docs may explain why readiness stays unreleased, but must not prepare release notes,
checklists, publication evidence, tags, packages, images, or public write-beta wording
until an explicit owner/PM release-candidate decision exists.

This boundary applies to status summaries too. A summary may say that evidence was
accepted narrowly and that checks passed, but it must immediately preserve the
current state: no release, no public write beta, and no broader write-safety claim.

Reviewer-facing docs should separate three things:

1. evidence that was accepted narrowly for maintenance;
2. blockers that still prevent a release-state change;
3. the owner/PM approval that must happen before release-candidate preparation.

If a sentence blurs those categories, rewrite it toward the no-release state.

## Maintenance-document wording pattern

Prefer wording that makes the state machine explicit:

- current state: `NO_RELEASE_KEEP_MAINTENANCE`;
- evidence role: narrow, redacted maintenance evidence;
- missing switch: explicit owner/PM release-candidate approval;
- forbidden implication: clean checks or completed docs publish owner-writebeta.

Avoid wording that treats remaining blockers as a checklist a worker can finish and
then ship. This package is allowed to improve explanations only. It does not open a
release path, does not rename the current public release line, and does not convert
owner-writebeta into an available feature.

## No-release document is not a release artifact

This file and its companion pages exist to prevent a release signal, not to stage
one. They may be linked from status or handoff docs as the reason owner-writebeta
stays unreleased, but they must not be copied into release notes, announcement
drafts, tag messages, package metadata, or image descriptions.

Safe use:

- quote the current decision as `NO_RELEASE_KEEP_MAINTENANCE`;
- explain that owner approval is absent;
- point reviewers to narrow maintenance evidence without broadening it.

Unsafe use:

- treat this packet as a release dossier waiting for final approval;
- promote the explanation into publication copy;
- use the existence of a no-release doc as proof that release review is complete.

The document name includes release terminology only because it records a negative
decision. It does not authorize any positive release action.

## Release-state invariant

This package can improve explanations, but it cannot change release state.

The invariant is:

```text
owner-writebeta readiness docs != owner-writebeta release authorization
owner-writebeta release authorization requires a later explicit owner/PM switch
```

For this task, all of the following remain true even after clean verification:

- no tag or GitHub release is created;
- no package, image, or public artifact is prepared;
- no public write-beta, stable, production-ready, or security-audited wording is
  added;
- no broad compatibility or real/private/original/working/only-copy safety claim
  is added;
- `GNUCASH_WRITES_ENABLED=false` remains the default and enabled writes remain
  `APP_ENV=test` gated.

A future release-candidate task must start from a new explicit owner/PM decision.
It must not infer approval from this no-release documentation packet.

## Dependency-order guard

Do not describe owner approval as an item that naturally follows the current
readiness packet. In this state, approval is not the last checklist row; it is the
missing switch that decides whether a release-candidate checklist may exist at
all.

## Decision-source hierarchy

When multiple docs, handoffs, generated backlog notes, or clean verification runs
are visible, use this hierarchy to avoid accidentally upgrading maintenance work
into release work:

1. A later explicit owner/PM release-candidate decision that names scope and
   allowed artifacts can change the release state.
2. Current no-release docs and status pages explain the existing state while that
   decision is absent.
3. Historical handoffs and accepted evidence show what was reviewed, but they do
   not grant publication permission.
4. Generated task metadata and passing checks show the worker stayed inside a
   safe maintenance envelope, not that owner-writebeta is ready to publish.

If item 1 is missing, the rest of the material must be read as support for
`NO_RELEASE_KEEP_MAINTENANCE`. Do not combine lower-priority sources into implied
approval.

Safe phrasing:

- readiness evidence has been recorded for maintenance review;
- release-candidate preparation is blocked until a later explicit owner/PM
  decision names the scope;
- until then, no publication artifacts are prepared.

Repeated documentation passes do not weaken this dependency order. If another
worker can only clarify the no-release explanation, that is maintenance work and
must not be reported as progress toward publication.

Unsafe phrasing:

- the package is ready to release after approval;
- remaining blockers are only administrative;
- a worker may finish the listed items and publish.

## Future-task triage rule

When a future task references owner-writebeta release material, classify it before
editing:

| Prompt type | Allowed outcome | Stop line |
| --- | --- | --- |
| No-release explanation | Clarify conservative docs and status links | Do not create release artifacts |
| Evidence reconciliation | Record narrow, redacted maintenance evidence | Do not change release state |
| Release-candidate preparation | Proceed only if explicit owner/PM approval names scope | Stop if approval is absent |

This triage is intentionally conservative. A task that mentions release but only
authorizes no-release documentation stays in the first row. A worker must not
upgrade it into the third row by completing checks, collecting handoffs, or
rewriting blockers as tasks.

## Repeated-task guard

A repeated or backfilled task identifier does not roll the repository back to an
earlier release decision. If the tree already contains newer conservative
no-release docs, treat the task as a maintenance clarification pass only.

Safe handling for repeated no-release tasks:

1. Read the latest tracked no-release docs and handoffs first.
2. Preserve newer conservative wording unless it conflicts with the current prompt.
3. Add only clarifications that make the no-release boundary clearer.
4. If no scoped clarification remains, report a clean no-op instead of inventing
   release work.

This keeps generated documentation loops from turning old task names into a path
toward publication. The current state remains `NO_RELEASE_KEEP_MAINTENANCE` until
a later explicit owner/PM release-candidate decision changes it.

## Documentation-only progress guard

A no-release documentation task may improve reader understanding, but it must not
be described as progress toward publishing owner-writebeta. Treat any wording
cleanup, navigation update, or verification pass in this area as maintenance
hygiene only.

Safe reporting for such a task:

- clearer explanation of why owner-writebeta stays unreleased;
- no release-state change;
- no new release-candidate scope;
- no publication artifact prepared.

Unsafe reporting would say that the docs are now closer to release, that approval
is the only remaining formality, or that a future worker can package the existing
readiness evidence. Those statements would convert maintenance wording into an
unauthorized public write-beta signal.

## Generated-task provenance guard

Generated backlog flags such as `generated-safe`, `no-release`, `docs-only`, or
`continue if docs remain conservative` describe the allowed maintenance scope for
the worker. They are not owner approval for a release-state change.

Treat generated task metadata as a safety envelope:

- it can allow conservative documentation edits;
- it can require checks and a safe commit;
- it can forbid tags, packages, images, dogfood, and GnuCash mutations;
- it cannot supply the missing owner/PM release-candidate switch.

If a future task is generated from a backlog policy and asks only for release or
no-release documentation, keep the decision anchored to
`NO_RELEASE_KEEP_MAINTENANCE`. Do not reinterpret the existence of another worker
task as proof that owner-writebeta is ready to package, announce, or publish.

## Prompt-authority guard

A bounded worker prompt can authorize conservative documentation maintenance, but
it cannot silently override the no-release decision. Treat the prompt action and
the release-state action as separate approvals:

| Prompt authorizes | Meaning here | Still forbidden |
| --- | --- | --- |
| Improve no-release docs | Clarify the explanation | Prepare release artifacts |
| Run verification checks | Prove guarded docs still pass | Claim release readiness |
| Commit safe docs-only edits | Keep the tree clean for the supervisor | Change public write posture |

If a task says to continue only while docs remain conservative, the safe result is
better maintenance wording plus the same release state. It is not a substitute for
owner/PM release-candidate approval.

## Historical-evidence interpretation

Historical gate docs, handoffs, and issue-state snapshots remain useful audit
records, but they are not live release instructions. A later closure, reopened
issue, green check run, or wording cleanup can update the maintenance history
without changing the owner-writebeta release state.

When older release-status docs disagree with newer conservative status summaries,
read them as dated evidence unless a later explicit owner/PM decision changes the
state. Do not edit historical gate records into publication proof, and do not use
newer evidence reconciliation to infer approval that was absent in the original
no-release packet.

Safe status wording should say:

- the historical record is maintenance evidence;
- later reconciliation does not create release authorization;
- owner-writebeta remains unreleased until an explicit owner/PM release-candidate
  task names the scope.

Unsafe status wording would say that a historical blocker is now cleared and
therefore the unreleased owner-writebeta line may be packaged or announced.
