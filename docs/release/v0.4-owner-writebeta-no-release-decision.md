## PM decision

Do not prepare, tag, publish, or claim `v0.4.0-owner-writebeta` in this package.

## Why

- W3 copied-book evidence is accepted narrowly, but only for one staged outside-git copied/restorable
  target and exact CREATE 2 / PATCH 1 / DELETE 1 operation counts.
- #36 remains open for remaining controlled-write gates, PM closure acceptance, real-book boundary,
  and supported-version compatibility posture.
- #22 is closed narrowly for one Desktop-generated synthetic SQLite fixture, but that closure is
  read-only synthetic evidence only and does not prove owner-writebeta write compatibility.
- #28 was improved for release-reviewer readability, but readability cleanup is not a reason to
  publish writebeta.
- A pre-release now could still be misread as public write beta or broader real-book/write safety.
- Passing repository health checks do not override the missing owner approval for release publication.
- Owner approval is the release-state switch; until that switch exists, readiness docs stay
  maintenance-only and must not become release-candidate artifacts.

## What remains true

- `v0.5.1-public-readonly-beta` is not published.
- `v0.4.0-owner-writebeta` is not published.

- Enabled write-alpha/writebeta remains `APP_ENV=test` gated.
- No public write beta, stable, production-ready, security-audited, broad compatibility, or
  only-copy safety claim is made.

## Documentation boundary

Docs may explain why readiness stays unreleased, but must not prepare release notes,
checklists, publication evidence, tags, packages, images, or public write-beta wording
until an explicit owner/PM release-candidate decision exists.

This boundary applies to status summaries too. A summary may say that evidence was
accepted narrowly and that checks passed, but it must immediately preserve the
current state: no release, no public write beta, and no broader write-safety claim.

Reviewer-facing docs should separate three things:

1. evidence that was accepted narrowly for maintenance;
2. blockers that still prevent a release-state change;
3. the owner/PM approval that must happen before release-candidate preparation.

If a sentence blurs those categories, rewrite it toward the no-release state.

## Maintenance-document wording pattern

Prefer wording that makes the state machine explicit:

- current state: `NO_RELEASE_KEEP_MAINTENANCE`;
- evidence role: narrow, redacted maintenance evidence;
- missing switch: explicit owner/PM release-candidate approval;
- forbidden implication: clean checks or completed docs publish owner-writebeta.

Avoid wording that treats remaining blockers as a checklist a worker can finish and
then ship. This package is allowed to improve explanations only. It does not open a
release path, does not rename the current public release line, and does not convert
owner-writebeta into an available feature.

## Release-state invariant

This package can improve explanations, but it cannot change release state.

The invariant is:

```text
owner-writebeta readiness docs != owner-writebeta release authorization
owner-writebeta release authorization requires a later explicit owner/PM switch
```

For this task, all of the following remain true even after clean verification:

- no tag or GitHub release is created;
- no package, image, or public artifact is prepared;
- no public write-beta, stable, production-ready, or security-audited wording is
  added;
- no broad compatibility or real/private/original/working/only-copy safety claim
  is added;
- `GNUCASH_WRITES_ENABLED=false` remains the default and enabled writes remain
  `APP_ENV=test` gated.

A future release-candidate task must start from a new explicit owner/PM decision.
It must not infer approval from this no-release documentation packet.

## Dependency-order guard

Do not describe owner approval as an item that naturally follows the current
readiness packet. In this state, approval is not the last checklist row; it is the
missing switch that decides whether a release-candidate checklist may exist at
all.

Safe phrasing:

- readiness evidence has been recorded for maintenance review;
- release-candidate preparation is blocked until a later explicit owner/PM
  decision names the scope;
- until then, no publication artifacts are prepared.

Repeated documentation passes do not weaken this dependency order. If another
worker can only clarify the no-release explanation, that is maintenance work and
must not be reported as progress toward publication.

Unsafe phrasing:

- the package is ready to release after approval;
- remaining blockers are only administrative;
- a worker may finish the listed items and publish.

## Future-task triage rule

When a future task references owner-writebeta release material, classify it before
editing:

| Prompt type | Allowed outcome | Stop line |
| --- | --- | --- |
| No-release explanation | Clarify conservative docs and status links | Do not create release artifacts |
| Evidence reconciliation | Record narrow, redacted maintenance evidence | Do not change release state |
| Release-candidate preparation | Proceed only if explicit owner/PM approval names scope | Stop if approval is absent |

This triage is intentionally conservative. A task that mentions release but only
authorizes no-release documentation stays in the first row. A worker must not
upgrade it into the third row by completing checks, collecting handoffs, or
rewriting blockers as tasks.
