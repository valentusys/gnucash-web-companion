# v0.2.5-writealpha No-Release Verdict

Date: 2026-05-21
Phase: 221
Verdict: `NO RELEASE — do not publish v0.2.5-writealpha`

## Decision

`v0.2.5-writealpha` is not published.

The candidate remains absent as:

- no local annotated tag;
- no remote tag;
- no GitHub pre-release/release;
- no package, binary artifact, Docker image, or production deployment.

## Blocking reason

Phase 220 exposed a release blocker in the bounded synthetic/disposable write-alpha DELETE evidence:

- default-read-only API/browser dogfood passed with `GNUCASH_WRITES_ENABLED=false`;
- write-alpha preflight, create smoke, and PATCH smoke passed;
- DELETE route execution succeeded and redacted inspection confirmed API/runtime absence, one successful DELETE audit row, bounded backup evidence, and stale-released/not-active lock evidence;
- however, the helper failed because backup file count did not increase by exactly one after DELETE;
- redacted inspection showed three successful backup-bearing route-family audit entries but only two backup files.

Because a write-alpha maintenance release requires bounded create/PATCH/DELETE backup/audit evidence, this mismatch blocks publication.

## What remains safe to keep

Cycle-2 docs, tests, status updates, default-read-only dogfood, upgrade smoke, public status guard, unavailable-book handling, CSV/list parity, audit-summary pagination, and localization glossary work are safe to keep on `main`.

## Safety boundaries retained

- `GNUCASH_WRITES_ENABLED=false` remains default.
- `APP_ENV=test` remains required for explicit write-alpha execution.
- Write-alpha evidence remains synthetic/disposable only.
- No real/private-book or only-copy write safety is claimed.
- The project remains pre-alpha, not production-ready, and not security-audited.

## Next safe engineering phase

Investigate the DELETE backup-count anomaly before any new release attempt:

1. Reproduce with a fresh synthetic/disposable runtime copy only.
2. Add targeted tests or helper assertions for backup file creation/counting versus backup-bearing audit rows.
3. Verify no audit row can claim backup-bearing success without a corresponding readable backup artifact, or document/remediate the exact reason if the helper count logic is wrong.
4. Rerun bounded create/PATCH/DELETE write-alpha evidence and default-read-only reset smoke.
5. Only after green evidence, run a new release gate.

## Phase 227 status note

Phases 222–226 later remediated and re-verified the blocker in synthetic/disposable scope: backup artifact identity was hardened against rapid timestamp collisions, DELETE restore proof passed, the create/PATCH/DELETE matrix passed with matching redacted audit/backup evidence, and the default-read-only Docker/Caddy path passed afterward with `GNUCASH_WRITES_ENABLED=false`.

This closure is intentionally narrow. It closes the Phase 220 no-release blocker as synthetic evidence remediation only. It does not publish `v0.2.5-writealpha`, does not change the current public write-alpha release (`v0.2.4-writealpha`), does not enable writes by default, does not weaken the `APP_ENV=test` gate, and does not establish real/private-book or only-copy write safety.
