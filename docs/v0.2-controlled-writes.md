# v0.2 Controlled Writes Design

## Status

Design / experimental implementation only. Not part of v0.1.

Controlled writes are not part of MVP v0.1. MVP v0.1 remains read-only by default. Writes are experimental and disabled unless explicitly enabled. Do not use write mode with your only copy of a GnuCash book.

As of Phase 128, routed write-alpha endpoint execution is intentionally constrained to explicit test environment scope (`GNUCASH_WRITES_ENABLED=true` and `APP_ENV=test`) and copied/disposable fixture books. This is safety evidence only, not a real-user or production-book enablement path.

## Product boundary

v0.1 is a read-only companion for browsing one default GnuCash book. GnuCash Desktop remains the authoritative editor.

Controlled writes are post-MVP work. They are intentionally narrow and must not become collaborative accounting on top of GnuCash. If shared editing ever exists, it must be serialized and locked, not real-time collaborative editing.

The baseline product model remains multiple independent books with scoped access, not a family shared-wallet ledger.

## Required safety model

Before write mode can be considered usable beyond experiments, it requires:

- explicit feature flag (`GNUCASH_WRITES_ENABLED=true`)
- per-book write lock
- backup before every write
- audit log for routed write attempts, including failures after the route is entered
- dry-run validation endpoint
- Decimal/string money only
- no float arithmetic
- disposable test copy required
- clear UI warning before submit
- documented restore procedure

## Existing experimental implementation

The repository currently contains experimental controlled-write code, disabled by default:

- validation endpoint: `POST /books/{book_id}/transactions/validate`
- create transaction endpoint: `POST /books/{book_id}/transactions`
- patch transaction endpoint: `PATCH /books/{book_id}/transactions/{transaction_id}`
- `GnuCashWriteService`
- backup service
- audit logging through the app metadata DB
- file-based per-book write locking with `fcntl.flock()` under `/data/locks/` (Phase 21)
- frontend `/transactions/new` form, hidden unless writes are explicitly enabled

Phase 23 added backup restore smoke coverage proving that backups created before write operations can be restored and preserve the original disposable fixture state.

Phase 32 added committed disabled-write regression coverage proving that, with `GNUCASH_WRITES_ENABLED=false`, validate/create/patch return read-only 403 responses before `_write_service_for` / `GnuCashWriteService` is constructed. This is safety coverage only; it does not expand write support or make write mode production-ready.

Phase 36 added explicit frontend write-mode warnings and a required acknowledgement checkbox before final create submission. The warning states that controlled writes are experimental post-MVP functionality, MVP v0.1 remains read-only by default, `GNUCASH_WRITES_ENABLED=false` is the safe default, GnuCash Desktop remains the authoritative editor, and users must use disposable/test copies with backups.

Phase 123 started the write-alpha safety foundation without enabling writes by default. It added regression coverage proving the repository defaults remain disabled (`Settings.gnucash_writes_enabled is False`, `.env.example`, and Docker Compose default fallback), disabled write routes return 403 before book resolution or write-service construction, write-lock failures are audited as failed write attempts before any backup path is recorded, and service validation explicitly rejects split-count, non-zero-sum, invalid decimal, missing-account, invalid-date, and placeholder-account cases. This is safety coverage only; it does not enable write mode or broaden write capabilities.

Phase 124 hardened the first controlled transaction create flow for write-alpha test scope only. Enabled validate/create/patch routes now also require `APP_ENV=test`, so `GNUCASH_WRITES_ENABLED=true` in normal development/runtime scope still returns 403 before constructing a write service. Route-level integration tests copy the committed synthetic GnuCash SQLite fixture to a temporary path, then verify that a create request updates only that disposable copy, creates a pre-write backup, records a successful audit row with transaction id and backup path, releases the per-book lock, and preserves failure behavior for validation errors with failed audit/no backup/no lock leak. This does not add edit/delete/import/scheduled/account writes and does not make write mode safe for real books.

Phase 128 expanded write-alpha create-route safety evidence without enabling writes by default. Tests now exercise two parallel `POST /books/{book_id}/transactions` requests against a copied disposable fixture and verify that one succeeds while the contending request receives a lock-conflict error, the book remains balanced/intact with one new transaction, and both success/failure attempts are audited. Error-path coverage now forces a synthetic post-backup write failure and verifies that the per-book lock is released, the failed audit row records the backup path, the backup remains readable and matches the pre-write book state, and the disposable book is not mutated. A route test also proves read-only/viewer book access returns 403 before constructing the write service. The write lock now explicitly rejects re-entrant same-process acquisition for the same book key instead of replacing the active lock file descriptor.

## Known limitations

- piecash compatibility must be validated against supported GnuCash versions. No production write-mode guarantee.
- CSV export (Phase 24) is read-only; frontend amount range filters for browsing and CSV export were added in Phase 30. Export customization remains intentionally basic.
- Multi-book UI (Phase 20) is structural; full multi-user access control is post-MVP.

Resolved historical limitations:

- Phase 21 replaced the original process-local lock with `fcntl.flock()`-based file locking for multi-worker safety.
- Phase 22 added 30 integration tests against real disposable piecash books.
- Phase 23 added 6 backup restore smoke tests.
- Phase 30 added frontend amount range filters for read-only transaction browsing and CSV export.
- Phase 32 added disabled-write bypass regression coverage for validate/create/patch, including tests proving the write service is not constructed while writes are disabled.
- Phase 36 added clear UI warning and explicit acknowledgement coverage before final create submission.
- Phase 123 added write-alpha safety-foundation regression coverage for disabled-by-default route short-circuiting, default config proof, lock-failure audit evidence, and explicit create-validation guard evidence.
- Phase 124 added test-environment-only route gating plus copied-disposable-fixture create-route integration evidence for book-state read-back, backup, audit, lock release, and validation-failure handling.
